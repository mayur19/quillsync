# Requirements

This document lists the functional requirements (FR) and non-functional requirements (NFR) for quillsync. Every requirement traces to one or more backlog tickets in [../planning/backlog.md](../planning/backlog.md). The full FR-to-code-to-test mapping is in [requirements-traceability.md](requirements-traceability.md).

**Conventions**

- **Priority** uses MoSCoW: **M** (Must), **S** (Should), **C** (Could). Won't-have items for this release are listed in [PRD.md §4](PRD.md#4-goals-and-non-goals).
- **Status** is `implemented` only when every ticket listed for the requirement is `done` in the backlog. Otherwise it is `pending`. Any HTTP surface of a pending requirement already answers `501 NOT_IMPLEMENTED`, with the ticket ID in `error.details.ticket` (FR-006).
- Acceptance criteria (AC) are written to be verifiable by an automated test, unless they say otherwise.

**Totals:** 95 FRs (27 implemented, 68 pending) and 37 NFRs (14 implemented, 23 pending).

### E2: CRDT core

| ID     | Requirement                                                                                                                                   | Pri | Status      | Tickets                | Acceptance criteria                                                                                                                                                                                                                                                                                                    |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------- | --- | ----------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-019 | The document text is an RGA sequence CRDT. Concurrent inserts and deletes from any number of replicas converge to identical text.             | M   | implemented | QS-020, QS-021, QS-027 | Item IDs are `{client, seq}` with contiguous `seq` per client. Insert carries `origin` (the nearest visible item to the left, or null). Delete tombstones its target. The seeded property tests apply random concurrent schedules to three or more replicas in permuted orders and assert identical materialized text. |
| FR-020 | Remote ops are delivered causally, idempotently and in any arrival order.                                                                     | M   | implemented | QS-022                 | An op is integrated only when `seq == vector[client] + 1` and its origin or target is present. Otherwise it waits in the pending buffer. Ops with `seq <= vector[client]` are dropped. Feeding the same op set reversed, shuffled or duplicated gives identical state.                                                 |
| FR-021 | Large remote batches and rehydration use timestamp-tree materialization.                                                                      | M   | implemented | QS-023                 | Batches larger than 32 ops are merged by rebuilding the tree (O((n+k) log(n+k))). Property tests assert that the tree order equals the scan-integration order.                                                                                                                                                         |
| FR-022 | Ops are compressed into runs and encoded with a bounded binary codec for the wire and for storage.                                            | M   | implemented | QS-024                 | Consecutive single-client inserts become one run, and consecutive deletes become one run with target ranges. The codec uses LEB128 varints, a client-ID dictionary and UTF-8 text. Encode followed by decode is the identity. Malformed or truncated input throws `CodecError` (fuzzed).                               |
| FR-023 | A library computes which tombstones can be collected safely using causal stability.                                                           | M   | implemented | QS-025                 | Stable vector = pointwise minimum of the acknowledged vectors. A tombstone is removed only when its delete is stable and it has no retained children. Removal never changes the visible text or the positions of later integrations (tested).                                                                          |
| FR-024 | Cursor and comment positions are expressed as CRDT anchors. The editor converts textarea edits to ops with a minimal diff.                    | M   | implemented | QS-026                 | An anchor is the ItemId to its left, or null. It resolves to an index even when that item is tombstoned. A common-prefix and common-suffix diff produces at most one delete run and one insert run per change.                                                                                                         |
| FR-025 | Text supports formatting marks (bold, italic, inline code, link) as CRDT attributes that converge.                                            | M   | pending     | QS-040                 | Concurrent mark and unmark on overlapping ranges converge identically on all replicas. A link mark stores an href validated as `http`, `https` or `mailto`. Typing at the edge of a mark follows a documented expand rule (bold expands, link does not).                                                               |
| FR-026 | Documents are a sequence of typed blocks (paragraph, heading 1 to 3, bulleted or numbered list item, quote, code block) on the sequence CRDT. | M   | pending     | QS-041                 | Splitting a block with Enter and merging blocks with Backspace are expressible as ops and converge under concurrency. Changing a block's type is a last-writer-wins attribute ordered by (lamport, client).                                                                                                            |
| FR-027 | Blocks can be moved and reordered without duplication or loss under concurrent moves.                                                         | S   | pending     | QS-042                 | Two replicas moving the same block concurrently converge to a single position chosen by (lamport, client). A moved block keeps its ID, comments and anchors.                                                                                                                                                           |
| FR-028 | The CRDT locates items by visible index and by ItemId in O(log n) with an order-statistic B-tree.                                             | S   | pending     | QS-043                 | Index-to-item and item-to-index lookups and integration are O(log n), as shown by the benchmark (NFR-008). Behaviour is identical to the array implementation under the property tests.                                                                                                                                |
| FR-029 | Each user can undo and redo only their own changes.                                                                                           | M   | pending     | QS-044                 | Undo inverts the user's most recent local operation group as new forward ops. Undo never removes text typed by another user, including text typed inside the undone range.                                                                                                                                             |
| FR-030 | A large-scale fuzzing and benchmark harness exercises the CRDT.                                                                               | S   | pending     | QS-045                 | Runs 10^6 random ops across 8 replicas with a fixed seed and records ops/s, bytes per op and heap per item. It fails CI when a benchmark regresses by more than 20 %.                                                                                                                                                  |
| FR-031 | Documents can contain table blocks.                                                                                                           | C   | pending     | QS-046                 | Inserting a row or column concurrently with cell edits converges, and cell text is itself a sequence.                                                                                                                                                                                                                  |
| FR-032 | Documents can embed images stored on the server's local disk.                                                                                 | S   | pending     | QS-047                 | Uploads of PNG, JPEG, GIF or WebP up to 10 MB are content-type sniffed and stored under the uploads directory. The embed block references the upload ID, and images are served only to users who can read the document.                                                                                                |

### E3: Real-time sync

| ID     | Requirement                                                                                                              | Pri | Status      | Tickets        | Acceptance criteria                                                                                                                                                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------ | --- | ----------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-033 | Clients sync over a WebSocket. A handshake exchanges state vectors and returns only missing ops.                         | M   | implemented | QS-030         | `GET /api/v1/documents/:id/sync` upgrades for an authenticated member. The client sends `hello {clientId, vector, user}`, and the server replies `welcome {vector, runs, peers}`, where `runs` holds exactly the ops with `seq > vector[client]`. All frames are validated with the shared zod schemas. |
| FR-034 | Ops from one client are integrated, persisted, acknowledged and fanned out to every other socket in the room.            | M   | implemented | QS-030         | On `ops {runs}` the room integrates the ops through its per-room queue, persists the newly integrated ones, sends `ack {vector}` to the sender and `ops {runs, from}` to the other sockets. Duplicate ops are acknowledged but not re-broadcast.                                                        |
| FR-035 | The sync endpoint enforces Origin and role. Viewers and commenters are read-only.                                        | M   | implemented | QS-030, QS-011 | An upgrade with an Origin other than `APP_ORIGIN` or no session is rejected. An `ops` message from a viewer or commenter returns `error {code: FORBIDDEN}` and nothing is integrated.                                                                                                                   |
| FR-036 | Every integrated op is stored durably in an op log. A room is rehydrated from it on first join.                          | M   | implemented | QS-031         | Each batch is one `document_ops` row (binary payload, `seq_start` and `seq_end`, unique on document, client and `seq_start`). | FR-037 | Users see who else is in the document and where their carets are.                                                        | M   | implemented | QS-032, QS-035 | `presence {anchor}` is broadcast to peers with display name and a colour derived from the client ID. `peer-left` is sent when a socket closes. `GET /api/v1/documents/:id/presence` lists current peers. Remote carets stay attached to the right character while others type.                          |
| FR-038 | Members can list, create and open documents in their organization.                                                       | M   | implemented | QS-033         | `GET /api/v1/documents` lists only the caller's organization. `POST` requires `document:create`. `GET /:id` returns metadata, text, vector and op count, or 404 for another organization's document.                                                                                                    |
| FR-039 | The web client provides login, registration, an app layout and navigation that marks unbuilt areas as planned.           | M   | implemented | QS-034         | Unauthenticated users are routed to login. Navigation entries for pending features show a "Planned" badge with the ticket ID.                                                                                                                                                                           |
| FR-040 | Users co-edit plain text in a collaborative editor with remote carets.                                                   | M   | implemented | QS-035         | Two browsers typing at the same position concurrently end with identical text in which neither user's run is split (NFR-002).                                                                                                                                                                           |
| FR-041 | The client reconnects with backoff and resends unacknowledged ops, so edits made during a disconnect merge on reconnect. | M   | implemented | QS-036         | Backoff runs from 0.5 s to 10 s with jitter. After reconnecting, the client resends every queued op the server's vector does not cover, and the server dedupes. Edits survive only while the tab stays open (see FR-085).                                                                               |
| FR-042 | A rich-text editor surface (contenteditable) maps DOM selections and IME composition to CRDT ops.                        | M   | pending     | QS-050         | Composition in Japanese, Chinese and Korean IMEs and dead-key input produce one insert run on `compositionend`. | FR-043 | Presence shows selection ranges, idle state and an optional follow mode.                                                 | C   | pending     | QS-051         | Remote selections render as highlighted ranges. A peer becomes idle after 60 s without input. Follow mode scrolls to the followed peer's caret.                                                                                                                                                         |
| FR-044 | The server applies backpressure and limits op rate per connection.                                                       | S   | pending     | QS-052         | A connection exceeding the configured ops per second receives `error {code: RATE_LIMITED}` and is closed after a grace period. Sending to a slow socket is bounded by a buffered-bytes threshold.                                                                                                       |
| FR-045 | Ops are fanned out across API nodes through PostgreSQL LISTEN/NOTIFY.                                                    | S   | pending     | QS-053         | Two API processes serving the same document deliver each other's ops to their sockets. A NOTIFY payload carries the document ID and the `document_ops` ID range, never the op bytes.                                                                                                                    |
| FR-046 | Each room has one owning node, held by an advisory lock, with failover.                                                  | C   | pending     | QS-054         | Only the lock holder integrates and persists ops. Followers forward to it. If the owner dies, another node takes the lock and serves the room within the NFR-033 bound.                                                                                                                                 |
| FR-047 | Op batches can be sent as binary WebSocket frames.                                                                       | C   | pending     | QS-055         | Binary frames carry the codec payload. A client that does not negotiate binary keeps JSON. Both forms decode to identical runs.                                                                                                                                                                         |
| FR-048 | Permission changes take effect on sockets that are already open.                                                         | M   | pending     | QS-056         | Revoking access or downgrading to viewer closes the socket or stops accepting `ops` within the NFR-036 bound, without a reconnect.                                                                                                                                                                      |
| FR-049 | Presence scales to 100 or more concurrent editors in one document.                                                       | C   | pending     | QS-057         | Presence updates are throttled per client and sampled for rooms above 50 peers, within NFR-010.                                                                                                                                                                                                         |

### E4: Persistence and compaction

| ID     | Requirement                                                                                                  | Pri | Status  | Tickets | Acceptance criteria                                                                                                                                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------ | --- | ------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-050 | The server periodically writes document snapshots to PostgreSQL.                                             | M   | pending | QS-060  | A snapshot (encoded state, state vector, op-log high-water ID) is written after 500 new ops or 5 minutes of activity, and on room unload. `POST /api/v1/documents/:id/snapshots` forces one. Rehydration loads the latest snapshot plus the op-log tail.                                |
| FR-051 | Op-log rows fully covered by the latest snapshot are compacted.                                              | M   | pending | QS-061  | Rows below the snapshot high-water ID are deleted in a transaction. Rows still needed by a version checkpoint or an unacknowledged replica's delta are kept. Rehydrated text is identical before and after compaction.                                                                  |
| FR-052 | The server tracks each replica's acknowledged vector and runs tombstone GC at the causal-stability frontier. | M   | pending | QS-062  | `document_replicas` stores client ID, acknowledged vector and `last_seen_at`. GC uses the library from FR-023 with the pointwise minimum of active replicas. Visible text is unchanged after GC.                                                                                        |
| FR-053 | Replicas that have been silent too long are evicted. On return they resync from a snapshot.                  | S   | pending | QS-063  | A replica with no acknowledgement for the configured number of days is removed from the GC frontier. When it reconnects with a vector below the compaction point, it receives `error {code: RESYNC_REQUIRED}` and reloads, and its unacknowledged local ops are rebased as new inserts. |
| FR-054 | Operators can verify backup and restore with a pg_dump round trip.                                           | M   | pending | QS-064  | `./run.sh` gains a backup verification step: dump, restore to a scratch database, compare document text and vectors for every document, and exit non-zero on any mismatch.                                                                                                              |
